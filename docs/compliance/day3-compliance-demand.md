# Day 3 — Compliance Demand Scenario

## Scenario

The simulated Security Audit Team has moved the PCI-DSS review forward. The platform must show how Kubernetes controls map to compliance expectations.

## Response

The platform responds by:

1. Separating dev, staging, and prod at cluster boundaries.
2. Separating four functional domains with namespaces.
3. Applying ResourceQuota and LimitRange controls to every application namespace.
4. Defining a six-persona least-privilege RBAC model for Day 4.
5. Designing default-deny network isolation for Day 5.
6. Maintaining evidence in version-controlled Markdown and YAML.
7. Explicitly marking future-phase controls rather than claiming they already exist.

## Compliance boundary

The project treats PCI-sensitive payment processing as a protected workload domain. The architecture does not assume that namespace separation alone proves PCI compliance. It is one layer in a broader defence-in-depth control set.

## Evidence generated by Day 3

- 12 application namespaces
- 12 ResourceQuota objects
- 12 LimitRange objects
- PCI-DSS mapping draft
- Compliance demand response

## Audit principle

Every control should answer three questions:

**What is the control? → Where is it configured? → How will it be tested?**
